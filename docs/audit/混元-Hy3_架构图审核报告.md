# 腾讯混元 Hy3（Hunyuan Hy3）3D 架构图 · 官方一致性审核报告

**审核对象**：`hunyuan-hy3-3d-architecture.html`（云端资料库 v18）、`index.html`（导航入口）
**审核日期**：2026-09-13
**审核方式**：独立子代理审核（不共享开发上下文，自行联网取一手材料）+ 开发方二次复核

**结论**：**发现 3 处实质性错误、2 处中度问题、9 处需收紧的表述，已全部修正（共 36 处）。** 另有 **22 组经核对确认无误**，包括所有最容易被挂错实体的数字（295B / 21B / 3.8B / 80 层 / 13,312 / 1,536）。

> 审核方还做了一次**独立的参数规模自洽性验算**：按 79 个 MoE 层 × (192+1) 专家 × 3 个矩阵 × 4096 × 1536，加注意力与嵌入，得 **≈295B 总参、≈21B 激活**，与官方口径吻合 —— 说明图中的架构数字彼此自洽，不是拼凑出来的。**本套未发现张冠李戴，也未发现图文自相矛盾。**

## 一、实质性错误（3 处，已修正）

### E1 `enable_moe_fp32_combine` 取值写反，导致结论方向相反

| 项 | 内容 |
|---|---|
| 图中原写 | 节点 13：「配置里还有 `enable_moe_fp32_combine = true`，说明 MoE 的合并计算在精度上做了单独处理」，data 字段亦列 `= true` |
| 官方口径 | **已发布权重（HF 与 ModelScope 双源逐字一致）均为 `"enable_moe_fp32_combine": false`**。审核还逐个核对了 HF 仓库的 4 个修订（2026-07-06 首发 / 07-17 / 07-20），**全部是 false**，所以不是「发布后被改掉」 |
| 我为什么会错 | transformers 的 `HYV3Config` **默认值**是 `true`（集成源码 `configuration_hy_v3.py`），而我在数据段的注释里自称「凡『config 口径』= transformers 集成文档」，等于照抄了默认值。而这个开关的含义是「共享专家与路由结果**是否在 fp32 下相加**」——取 `false` 时**恰恰不做** fp32 合并，所以我的结论正好说反了 |
| 修正 | 改为「已发布权重里 `enable_moe_fp32_combine = false`：共享专家与路由输出按模型 dtype 直接相加，并未做 fp32 合并。（transformers 集成文档里这个字段的默认值是 true，与已发布权重不是一回事，别混用。）」 |

### E2 `64 × 128 = 4,096` 算错了，应为 8,192

| 项 | 内容 |
|---|---|
| 图中原写 | 节点 04：「head dim 128 且 64 个查询头，两者相乘恰好等于隐藏维度 4,096」；内部薄板写 `64 × 128 = 4,096` |
| 官方口径 | config 为 `hidden_size=4096`、`num_attention_heads=64`、`head_dim=128`；集成源码 `q_proj = nn.Linear(hidden_size, num_attention_heads * head_dim)`，即 Q 投影输出 = **64 × 128 = 8,192**，`o_proj` 输入同为 8,192。这是一个 **head_dim 不按 hidden/heads 切**的宽头设计（4,096 ÷ 64 = 64 ≠ 128） |
| 我为什么会错 | 把「head_dim = hidden_size / num_heads」这条常见经验当成了本模型成立的前提，做了一次没验证的等式联想 |
| 修正 | 改为「head_dim 128 与隐藏维度 4,096 不是整除关系（4,096 ÷ 64 头 = 64 ≠ 128）：Q 投影的输出维度是 64 × 128 = 8,192，约为隐藏维度的 2 倍，最后由 o_proj 再投回 4,096」 |

### E3 「2026 年 1 月底启动基础设施重建」被我写成官方说法

| 项 | 内容 |
|---|---|
| 图中原写 | 节点 12：「官方新闻提到这次迭代的底层背景：从 2026 年 1 月底开始重建基础设施」；节点 15 时间线亦含该日期 |
| 官方口径 | 腾讯官网发布稿（2026-07-06）只说「**4 月 23 日发布的 Hy3 preview 为混元重建后首个版本**」，**未给出重建起始日期**；官方模型卡与预览版公告同样没有。腾讯自有渠道还互相打架：腾讯云开发者社区一篇写「2026 年 1 月重建、1 月底 Hy3 Preview 启动训练」，另一篇预览期文章写「今年 2 月全面重建」 |
| 我为什么会错 | 把「1 月底启动 Preview 训练」与「1 月底启动基础设施重建」两件事合并了，并把它挂到了「官方新闻」名下 |
| 修正 | 节点 12 改为「官方发布稿确认 Hy3 preview 是『混元重建后首个版本』，即 RL 基础设施在重建中被重写过；但官方从未给出重建的起始日期（腾讯自有渠道有 1 月与 2 月两种说法，口径不一致，本图不采信具体月份）」；节点 15 时间线删去该日期，并补一句「官方未给出基础设施重建的起始日期」 |

## 四、重点问题逐条核查结果

| 我的疑问 | 核查结论 |
|---|---|
| **295B 是总参还是激活？** | 295B = 总参，21B = 每 token 激活；「2950 亿 / 210 亿」为官方原话。7% 是推算 |
| **3.8B 是主干还是额外？** | **额外**。模型卡把 Total 295B 与 MTP Layer Parameters 3.8B 分列；ModelScope 仓库实际权重 298.79B ≈ 295+3.8，佐证 MTP 不计入主干 |
| **「80 层」含不含 MTP？** | 官方写 `Number of Layers (excluding MTP layer) = 80`，MTP 层数 1 → 图中「80 + 1」正确 |
| **13,312 是稠密层还是专家层？** | **稠密层**（`intermediate_size=13312`）；专家侧是 1,536。图中归属正确 |
| **1,536 是谁的维度？** | **专家**（`moe_intermediate_size` / `expert_hidden_dim`）。共享专家宽度 = 1,536 × 1 = 1,536 |
| **第 1 层稠密、其余 79 层 MoE？** | 正确。`first_k_dense_replace=1`；`mlp_layer_types` 默认 = `["dense"] + ["sparse"]×79` |
| **每层 192 路由 + 1 共享、top-8？** | 正确。`num_experts=192`、`num_shared_experts=1`、`num_experts_per_tok=8`；vLLM 官方 recipe 与 SGLang cookbook 亦明文一致 |
| **GQA 64 Q / 8 KV、head dim 128、attention_bias=false？** | 全部正确。**但「64×128=4,096」错**，见 E2 |
| **QK-Norm 是 Q/K 的 per-head RMSNorm？eps=1e-5？** | 正确（`q_norm/k_norm = HYV3RMSNorm(head_dim, rms_norm_eps)`，作用在逐头 128 维上）。⚠ 审核提醒：NVIDIA NeMo 文档的默认 eps 是 1e-6、`router_scaling_factor` 是 1.0、`vocab_size` 是 129,280 —— **与腾讯官方 checkpoint 不一致，属第三方默认值陷阱**；图中取 1e-5 是对的 |
| **sigmoid 打分 + per-expert bias + 无辅助损失？** | 三者均正确（`moe_router_use_sigmoid=true`、`moe_router_enable_expert_bias=true`、集成代码 `aux_loss=None`）。⚠ 「aux_loss 恒为 None」的出处是**集成代码**而非 config；「可学习」表述有误，见中度问题 2 |
| **router_scaling_factor = 2.826？** | 正确；官方定义为「top-k 路由权重的缩放系数」→ 已按其定义改写 |
| **tie_word_embeddings = false？** | 正确 |
| **`enable_moe_fp32_combine = true`？** | **错误，实为 false**，见 E1 |
| **256K 是否原生、是否需 RoPE 缩放？** | config `max_position_embeddings=262144`、无 rope_scaling → 不需缩放，「原生」成立但属推导。⚠ 集成文档默认值是 131072(128K)，照抄默认值会写错成 128K；图中取 256K 正确 |
| **BF16 / FP8 分别适用于谁？** | 官方「Supported Precisions: BF16」指主权重；Hy3-FP8 是另发的量化 instruct 权重，单独一个仓库条目。图中区分正确 |
| **reasoning_effort 三档、no_think 默认、temp 0.9 / top_p 1.0？** | 全部正确，与模型卡 Quickstart 逐字一致 |
| **「快慢思考融合」是官方说法？** | 是。官网发布稿原文「Hy3 是一个快慢思考融合的模型」 |
| **「而不是像上一代那样拆成两个模型」？** | **无依据且与官方冲突**，已删除 |

## 六、审核局限

1. **huggingface.co 直连被阻断**：模型卡与 config.json 经 `hf-mirror.com` 取得，并用 **ModelScope 官方 API 的 config.json 逐字交叉比对**（两站完全一致，含 `enable_moe_fp32_combine=false`），另用 HF 提交历史确认了 7-06 首发版的取值。CNB 的 raw 链接 404，未直接取到；四站链接以模型卡为准。
2. **未直接抓取 transformers 文档网页**：改用 GitHub 上 transformers 主干的 `configuration_hy_v3.py` / `modeling_hy_v3.py` 源码（同属官方集成代码），并以 NVIDIA NeMo Automodel 的 `HYV3Config` 文档作旁证 —— 但 NeMo 的默认值与腾讯官方 checkpoint **不一致**（eps 1e-6、router_scaling_factor 1.0、vocab 129,280），属第三方默认值陷阱，不能当官方口径。
3. **重建起始日期**：一手材料（官网发布稿、模型卡）完全没有；腾讯自有渠道有「1 月」「1 月底」「2 月」三种说法，已按「无一手依据」处理，图内不再出现具体月份。
4. **「50+ 产品团队」与「312 组对比」**：通过 HF 仓库提交历史取到 2026-07-06 版 README 原文，确认这两处措辞源自首发版官方模型卡、后被官方改动 —— 因此定性为「口径过时」而非「编造」。
5. **「per-expert bias 是否可学习」**：依据官方代码读作 `nn.Buffer`，据此提出质疑，但**未找到官方对偏置更新机制的说明**，故列为「需收紧」而非硬错误。
6. 图中若干「设计动机 / 好处」类因果解释（如节点 03、节点 05）在任何官方材料中都找不到对应表述，已统一按「图中解读」标注。
