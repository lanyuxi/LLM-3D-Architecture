## 一、实质性错误（6 处，已修正）

### E1 基座「每 MoE 层 64 个专家」——无出处，且疑似张冠李戴（散布 8 处）

| 项 | 内容 |
|---|---|
| 图中原写 | 页头副标题 `每 MoE 层 64 专家（基座）`；节点 04 `en:'2.4T · 64 专家 · top-k 8（基座）'`、inner `每 MoE 层 64 专家`、how `官方给出的锚点是「每 MoE 层 64 个专家」`；节点 06 `80% 全 64 专家 / 20% 取 32`；节点 09 的 ⚠ 句；页脚指标 `64 / EXPERTS / MoE LAYER / 基座 5.0 每层专家数` |
| 官方口径 | 技术报告全文里 `64` 只出现在两处语境：① `64-way expert parallelism`——**专家并行度**，不是专家数量；② 消融实验小节 `a small-scale MoE model with 64 experts, 454M activated parameters, and 3.2B total parameters`——一个 **3.2B 总参的小规模消融模型**。文心 5.0 官方博客同样只写「共享专家池」「<3% 激活率」，**没有专家数** |
| 我为什么会错 | 我把第三方解读里的「80% 的时间使用全部 64 个专家」直接当成了基座配置；实际那句出自报告的**消融模型**小节。更巧的是——**ERNIE 4.5 的 HuggingFace config.json 恰好是 `moe_num_experts:[64,64]`、`moe_k:8`**，即 64 专家 / top-8 正是**上一代**的公开配置，存在明显的张冠李戴嫌疑 |
| 修正 | 8 处全部改为「官方未公开基座的层数 / 每层专家数 / 默认 top-k」，并在节点 04 补上一条提醒：`别把报告里的「64-way 专家并行」误读成专家数量——那是并行度`；页脚指标改为红色高亮的 `未公开 / EXPERTS / TOP-K` |

## 四、确认无误的项（36 项，经一手材料核对，可放心保留）

**基座规模与稀疏性**：2.4 万亿总参（5.0 博客）· 超稀疏 MoE · 激活率低于 3%

**训练配方**：8K → 32K → 128K 三阶段 · Stage 1 WSD、warmup 2000 步 → 1e-4、batch 14M → 56M token · Stage 2 余弦退火 1e-4 → 1e-5 · MTP 损失权重 0.3 → 0.1 · RoPE base 1,000,000（自 8K 阶段起）

**基础设施**：4-way TP / 12-way PP / 64-way EP / ZeRO-1 / 上下文并行 · DeepEP · FP8 混合精度 · FlashMask

**弹性训练**：弹性深度 75% 全深度 / 25% 浅层 · 弹性宽度 80% / 20% · 弹性稀疏度 80% / 20%，降至原值 25% → 解码提速 >15% · 35.8% 总参 / 53.7% 激活参保接近满配（实体 5.0-Exp-EA） · 无辅助损失负载均衡、bias 更新 1e-4 → 1e-5

**主干机制**：模态无关路由 · 单一共享专家池 · token 不带模态标签 · 涌现式专家专业化及其分层规律 · Uni-RoPE（t, h, w）+ 中心对齐 · 文本与音频共享序列位置

**各模态细节**：文本 tokenizer UTF-16BE + BPE dropout + 中文长无空格短语过滤 · 音频 codec 12.5 Hz + RVQ 分层 + 首层语义并与 Whisper encoder 对齐蒸馏 + 多残差层专属 embedding 相加 · 视觉因果 2D 多尺度 → 因果 3D + bit-wise 渐进（低 bit → 高 bit） · 图像 K=4 / 视频 K=16 跨 4 帧 · NGoT 统一目标下视觉 NFSP、音频 NCP · tokenizer 与主干解耦、独立节点部署

**抽取叙事（本图主线）**：5.1 从 5.0 子模型矩阵中提取最优子结构并继承 5.0 知识 · 总参 ≈1/3 · 激活 ≈1/2 · 预训练算力 ≈同规模模型 6% · 「≈800B」自标为推算（算术正确）
